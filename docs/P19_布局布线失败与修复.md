# P19 布局布线失败（单点布线冲突）与修复

> 2026-10-28 · 现象："无法综合"。实际综合是**成功的**，失败在 `phy_1`（布局布线）。

## 1. 先分清是哪一步失败

`prj/log/td_2026-10-28_18-12-10.log`：

```
PRJ-1410 : Run syn_1 success.        <-- 综合没问题
PRJ-5303 WARNING: Run phy_1 failed.  <-- 布局布线挂了
```

`phy_1/run.log` 里真正的错误：

```
PHY-8023 ERROR: Location: (x17y63_local5), nets: u_wav/cur_clus[27] u_mnt/mux1_syn_2
RUN-8102 ERROR: Incremental route failed. ...
```

两个网络（音频播放器的簇号寄存器某一位、挂载模块的一个 mux）
抢同一个布线资源 `x17y63_local5`，detail route 过不去。

## 2. 为什么是这次才炸

| 时间 | 结果 |
|---|---|
| 10-27 23:32 及之前多次 | phy 正常 |
| 10-28 18:12（加了数码管百分比 + idle_tmo 之后） | **phy 失败** |

综合结果 LUT 9132/19600（47%），全局不拥塞，是**局部**布线冲突；
今天新增的 ~80 个寄存器把布局推到了临界点。

尝试过但**无效**的办法：

- `multi_try_route`（TD 的多轮布线）：4 秒返回，同一个违例，解决不了
- 重跑 P&R：placement 是确定性的，每次都在同一个 tile 失败

## 3. 有效修复：降低布线密度（等价 TD 内置 CongestionHigh 策略）

TD 自带策略库 `E:/TD/doc/strategies/official_strategy_ph1.json` 里有个
`CongestionHigh`，参数是：

```
place: opt_timing=high, opt_max_density=50, target_density=0.6,
       target_density_pp=0.7, enhanced_gp=on, non_crit_opt=on,
       enable_congestion_recovery=on
```

在 `prj/yuanshen_hdmi_Runs/phy_1/yuanshen_hdmi.tcl` 的 **opt_place 可编辑区**
（`### Editable zone for opt_place ###`）里，`place` 之前加上：

```tcl
  set_param place opt_timing high
  set_param place opt_max_density 50
  set_param place target_density 0.6
  set_param place target_density_pp 0.7
  set_param place enhanced_gp on
  set_param place non_crit_opt on
  set_param place enable_congestion_recovery on
```

结果：

| | 改前 | 改后 |
|---|---|---|
| route | 280 s 后失败 | **87 s 通过，0 违例** |
| bitgen | — | yuanshen_hdmi.bit (618 KB) |

⚠️ 这个脚本在 `prj/**/*_Runs/` 下，**不入 git**。如果哪天删掉/重置了 `phy_1` run，
TD 会重新生成默认脚本（参数丢失）。两条对策：

1. 重新把上面 7 行加回 `### Editable zone for opt_place ###` 之后；
2. 或者在 TD GUI 的"物理实现策略"里直接选 `CongestionHigh`（等价）。

## 4. 布线后时序（真正落地的数字）

| Path Group | WNS | 违例端点 |
|---|---|---|
| clk_pix（37.5MHz） | **+3.966 ns** | 0 |
| clk_mem（125MHz） | **+0.196 ns** | 0 |
| clk_mem_sft（125MHz 移相） | +17.380 ns | 0 |
| clk_sd（25MHz） | +5.555 ns | 0 |
| pix → mem（跨域） | −2.869 ns | 37 |
| mem → sft（SDRAM 内部） | −5.291 ns | 48 |

后两组是**跨时钟域**路径（FIFO 握手 / SDRAM 控制器内部相位），
历来都是负的，属于工具按整周期分析的假违例，与功能无关；
三个主时钟域这次全部为正余量。

## 5. 顺带说明：综合汇总里的 −5291ps 是什么

`flow_status` 打印的 `Setup WNS -5291ps / NUM_FEPS 240` 是**所有路径组的最差值**，
即上面那条 SDRAM 内部 `clk_mem → clk_mem_sft` 的跨相位路径。
从 10-27 16:58 到今天的每一次综合都是 −5291ps，与本次失败无关。
