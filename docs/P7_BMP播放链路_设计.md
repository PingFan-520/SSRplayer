## 1. 目标链路

```
SD 卡 (SPI)
   │ 512B 扇区
   ▼
扇区读取 / 扫描 ──> BMP 解码 ──> 帧缓存写（SDRAM, 2 块 buffer）
                                     │
                                     ▼
                              行读取 + 行缓冲 ──> 转场 ──> 亮度/对比度 ──> OSD 叠加 ──> HDMI
```

当前已完成中间两段（解码 + 帧存抽象），两端（SD、SDRAM）待接。

## 3. 待接：SDRAM 帧缓存

### 3.1 现状与约束

- 板上 SDRAM 是 **封装内 SIP**（2M×32，无外部引脚），只能用厂商控制器 `rtl/mem/sdram.v`。
- 该控制器依赖 `sdr_as_ram / sdr_init_ref / sdr_wrrd`（`.enc.v`），**ModelSim 10.1c 编译不了**
  （`in protected region` 报错），TD 的 `eg_phy_sdram_2m_32` 芯片模型也是全加密的，
  引脚级仿真读回全是 `z`。
- 结论：**SDRAM 这一块只能上板验证**，其余逻辑必须先在仿真里做干净。

### 3.2 接口（沿用参考工程的 App 接口）

| 信号 | 方向 | 说明 |
| --- | --- | --- |
| `App_wr_en / App_wr_addr / App_wr_din / App_wr_dm` | 出 | 连续拉高即连续写，单次 burst ≤ 256 字 |
| `App_rd_en / App_rd_addr` | 出 | 拉高发起读，可连续 |
| `Sdr_rd_en / Sdr_rd_dout` | 入 | 每字一个 valid 脉冲 + 32bit 数据 |
| `Sdr_init_done / Sdr_busy` | 入 | 初始化完成 / 忙 |

### 3.3 帧存规划

| 项 | 数值 |
| --- | --- |
| 一帧 1280×720 RGB565，2 像素/32bit 字 | 460,800 字 |
| 双 buffer | 921,600 字（2M 字的 44%） |
| 显示带宽 | 55.3M px/s → 27.6M 字/s，@100MHz 占 27.6% |
| 一行读取 | 640 字 / 17.1µs，页命中突发约 6.7µs |
| 写入（一张 640×480） | 153,600 字，摊到 0.3s 仅 0.5M 字/s |

结论：带宽余量充足，**读优先、写插空**即可，不需要复杂仲裁。

### 3.4 读侧结构

- 双行缓冲（2 × 640 字，BRAM 约 5Kb）。
- 显示第 N 行时，预取第 N+1 行；行首同步，预取在 17.1µs 内完成。
- 720p 的 30 行场消隐留给写通道和刷新。

## 5.2 SDRAM 仿真模型调研（lab_ex_4_tf_sdram_etnernet_pc，2026-10-22）

**结论：那个工程里也没有仿真模型，但型号是对的，而且拿到了一份"官方用法"。**

| 项 | 结果 |
| --- | --- |
| 器件 | `EG4S20BG256` —— 与本工程一致 |
| SDRAM | `EG_PHY_SDRAM_2M_32`（封装内 SIP，约束里没有 SDRAM 引脚）—— 一致 |
| 控制器 | `sdr_as_ram / sdr_init_ref / sdr_wrrd` 三个 `.enc.v` —— 同一套加密文件 |
| 仿真模型 | **没有**。`sim/` 只有 UDP 的 tb，全文不引用 SDRAM |
| 他们的仿真 | 直接绕开 SDRAM（`SIMULATION` 只用于声明引脚），SDRAM 靠上板自检 |

**但 `rtl/app_wrrd.v` 是厂商自带的写读自检**（写图案→读回→比对→点亮 `Check_ok` LED），
它把 App 接口的正确用法写死了：

| 规则 | 证据 |
| --- | --- |
| 读/写都是 **4 字突发** | `brust_rd_cnt` 0→3 循环，第 3 拍撤 en |
| 必须用 `Sdr_busy` 节流 | 所有请求条件都带 `!Sdr_busy` |
| 刷新期间不能发请求 | 条件带 `Sdr_init_ref_vld == 0` |
| 地址每个使能周期 +1 | `App_wr_addr <= w_addr_cnt`，`App_rd_addr` 在 en 时 +1 |
| 读数据 1:1 返回 | `Sdr_rd_en` 计数到 307199 |

自检范围 307,200 字（=640×480×32bit），刚好是我们一帧 640×480 的量。

> **对我们的直接影响**：`frame_buffer` 现在是"满了就连续发读"，既没有 `Sdr_busy`
> 节流，也不是 4 字突发。上板一定会和控制器打架。读路径的 bug 很可能就出在这里，
> 而不是 FIFO。下一步先按这张表改请求节奏，再重跑仿真。

## 5.3 APUG011 官方文档给出的硬约束（2026-10-23）

《APUG011 基于 ERAM 接口实现的高性能 SDRAM 读写 v1.2》把 App 接口的规则写清楚了，
其中**三条我们之前不知道，而且直接影响 frame_buffer 的正确性**：

| 约束 | 原文/依据 | 对我们的影响 |
| --- | --- | --- |
| **读写不能同时进行** | "不支持读写同时操作，读写需要独立排斥运行" | frame_buffer 现在边读边写 → 非法，必须时分复用 |
| **读延迟 10 拍** | "给出读使能信号后的 10 个时钟，开始给出有效数据" | 预取 FIFO 深度、预读时机都要按 10 拍留余量 |
| **刷新窗口禁止访问** | 读写前等 `Sdr_init_ref_vld` 变低 | 请求条件要加 `!Sdr_init_ref_vld` |

其他要点：

- 读写长度任意，但**尽量 4 的倍数**；地址跳跃只能在 4 字边界（`app_wr_addr[1:0]=0`）。
- 连续写入时 SDRAM 时钟要 **>64MHz**；`global_def.v` 的 `SDR_CLK_PERIOD` 必须按实际频率改
  （文档示例 150MHz，我们的参考工程写的是 125MHz，会影响刷新周期）。
- `Sdr_busy`：接口表写"暂不使用"，但第 7 节又要求"每次读写前判断"——文档自相矛盾，稳妥起见仍用它。
- 官方仿真流程（§5.2）：
  ```
  vlog -work work +incdir+$INCLUDE_PATH +define+SIMULATION ../source_code/rtl/*.v
  vlog -incr +incdir+$INCLUDE_PATH ../source_code/model/*.v
  vlog -incr +incdir+$INCLUDE_PATH +define+SIMULATION ../source_code/tb/*.v
  vlog -incr +incdir+$INCLUDE_PATH +define+SIMULATION ../prj/al_ip/*_sim.v
  ```
  关键是 `source_code/model/*.v`（SDRAM 行为模型）——**参考设计包里才有，我们盘上没有**。

## 5.5 SDRAM 引脚级仿真跑通（2026-10-23）

装上 **ModelSim SE-64 10.5**（`E://modelsim//win64`）后，加密控制器可以编译，
配合官方 `IS42s32200.v` 做引脚级仿真，**彻底解决了"SDRAM 不能仿真"的问题**。

### 仿真环境

```bat
vlog -work work105 +define+SIMULATION +incdir+rtl/mem ^
     rtl/mem/global_def.v rtl/mem/sdr_as_ram.enc.v rtl/mem/sdr_init_ref.enc.v ^
     rtl/mem/sdr_wrrd.enc.v rtl/mem/sdram.v ^
     APUG011_.../source_code/model/IS42s32200.v sim/tb_sdram_pin.v
vsim -c -t ps -voptargs="+acc" work105.tb_sdram_pin work105.glbl
```

> `sdram.v` 里芯片原型原本 `ifndef SIMULATION` 被注释掉了，仿真时必须恢复，
> 否则会报 `EG_PHY_SDRAM_2M_32 not found`。

### 三条实测出来的隐藏规则（文档里没写）

| # | 规则 | 证据 |
| --- | --- | --- |
| 1 | **App 地址是字节地址**：字索引 = App 地址 / 4 | 写 `addr=76960` 落在 `Bank0[19240]`；写 `addr=307840` 落在 `Bank0[76960]` |
| 2 | **写必须连续 4 拍**（一次 burst），中间插空拍整组丢弃 | 连续 8 拍写：引脚 `WR=2`，读回全对；每 2 拍写 1 次：引脚 `WR=0`，读回全 x |
| 3 | **初始化要等 2^17 个时钟**（125MHz ≈ 1.05ms） | `sdr_init_ref.enc.v` 明文里 `pwr_200ms_cnt[17]` 置位才启动 |

另外：这颗 SDRAM 的 tCK 最小 7ns（142MHz），我们按 125MHz 跑，模型不再报 `$period` 错。

### 地址空间的后果

21 位字节地址只能覆盖 **2MB = 512K 字**：

- 一帧 1280×720 RGB565 = 460,800 字 = 1.84MB → **单缓冲刚好放得下**；
- 双缓冲需要 3.7MB → **放不下**。

所以当前 `frame_buffer` 的 `BASE1` 也指向 0（单缓冲）。要做双缓冲只有两条路：
把 `App_wr_addr` 扩到 23 位（需换 IP），或者把分辨率降到 1024×576 以内。

### frame_buffer 的对应修正

| 问题 | 修正 |
| --- | --- |
| 地址语义 | 写/读地址都 `{字索引[18:0], 2'b00}` |
| 写 burst | 像素域先拼 32bit 字，mem 域攒 4 字后**连续发 4 拍** |
| afifo 是寄存器输出 | 用 `wpop -> wvld` 两拍链路取字，不能按 FWFT 直接用 `dout` |
| 初始化期间不许写 | `bsend` 加 `app_init_done` 门控 |

### 还没解决的

**落盘率只有约 1/5。** 一帧 153,600 字，App 侧发了 6 万多个写命令（引脚 `WR` 计数吻合），
但 SDRAM 里只有 2.4 万个位置有值，图像呈"虚线"状。

已排除的：
- 地址计算（`[bs]` 打印的 baddr 序列完全正确）
- 数据内容（渐变色方向对）
- FIFO 丢数（`wf_wr` 已改组合，`wr_ready` 反压有效）
- burst 之间加 gap（加 8 拍 gap 反而更差，只有首字落盘）

**怀疑：控制器对"背靠背 burst"或"非 4 字对齐的起始地址"处理有问题。**
具体现象是第一个 burst 的 `baddr` 是 307840（对齐），但紧接着变成 307848（+8 而非 +16），
说明第一个 burst 只攒了 2 个字就发了 —— 因为丢了一个像素导致 xw 从 161 开始。

**下一步建议**：
1. 先在 `tb_sdram_pin` 里做"连续发 N 个 4 字 burst（地址 +4 递增）"的纯控制器测试，
   确认控制器能连续接受多少个 burst、间隔要多少 —— 这是纯黑盒实验，最可靠；
2. 再回头修 `frame_buffer` 的像素配对（保证每行从对齐地址开始）。

## 5.7 决定性结论：720p60 的读带宽不够（2026-10-23）

### 先说好消息：写路径 100% 正确

逐行核对 SDRAM 内容（`[row]` 统计）：

```
[row] y=120 : 320/320   ...   y=135 : 320/320
```

图像区 y=120~599 共 480 行，每行 320 字**一个不缺**。之前看到的"条纹"是**读**出来的，不是写错的。

关键修复（两处，都在 `afifo`）：

| 问题 | 修正 |
| --- | --- |
| `afifo` 是寄存器输出，`rd_en` 后一拍 `rd_data` 才更新 | 新增 `rd_valid` 输出 |
| `rd_empty` 是跨时钟同步的，FIFO 接近空时滞后，只看 `rd_en` 会**把同一个字重复取两次** | `rd_valid <= rd_en & ~rd_empty`，`frame_buffer` 用它驱动 `wvld` |

修完 `[tk]` 追踪变成 `xw=160,161,162,163`（每字 +1），地址 `baddr` 每 +16 字节，完全正确。

### 再说坏消息：控制器读带宽只有 27.5M 字/s

显示期间实测（`[fr]` 打印）：

```
busy=77%   rd_en=22%
```

换算：`0.22 × 125MHz = 27.5M 字/s`。

而 720p60 全屏读需要：

```
1280×720/2 = 460,800 字/帧 × 60Hz = 27.6M 字/s
```

**刚好临界，甚至略低。**

更直观的算法：每行 1650 拍，读使能只占 22% → **363 字/行**，而一行要显示 1280 像素 = **640 字/行**。缺 43%。

### 为什么 busy 这么高

`ACT` 命令数和 `READ` 命令数几乎 1:1（`ACT=1027124`、`RD=988792`），说明**控制器每次访问都重新 ACTIVE + PRECHARGE，没有行缓存**。这是厂商 IP 的简化设计，不是我们的用法问题。

单次 burst 4 字要 ~10 个周期（ACT + READ×4 + PRE），4/10 = 40%，再叠加刷新和仲裁，实测 22%。

### 三条出路

| 方案 | 读需求 | 余量 | 改动量 |
| --- | --- | --- | --- |
| **A. 只读图片区域**（640×480=153,600 字/帧） | 9.2M 字/s | **3 倍** | 中：读侧改成行缓冲，黑边输出 0 |
| B. 降分辨率 1024×576 | 17.7M 字/s | 1.5 倍 | 小：改时序参数 + PLL |
| C. 720p30（每帧读两次） | 13.8M 字/s | 2 倍 | 小：读地址每两帧循环一次 |

**推荐 A**：图片本来就是 640×480，黑边根本不需要从 SDRAM 读，白白浪费 2/3 带宽。
顺带还能把 FIFO 从"整帧顺序流"改成"行缓冲"，逻辑更简单。

## 5.8 黑盒实验把控制器的规则彻底摸清了（2026-10-23 傍晚）

用 `sim/tb_sdram_burst.v` 做了四组写 + 两组读，结果如下：

### 写

| 组 | 条件 | 结果 |
| --- | --- | --- |
| A | 200 个 burst 背靠背（地址 +16 字节步进） | **800/800 全对** |
| B | 每个 burst 后 1 拍 gap | 32/32 |
| C | 每个 burst 后 4 拍 gap | 32/32 |
| D | 32 拍连续（地址 +4 字节） | 32/32 |

**结论：写完全支持背靠背，不需要 gap。**之前加 gap 反而有害，已回退。

> 顺带修正了一个方法论错误：早先 `tb_sdram_pin` 用"地址 +1 连续 8 拍"验证，
> 那实际是两个**重叠**的 burst（索引 A/4..A/4+3 与 A/4+1..A/4+4），
> 读回"全对"属于同址覆盖的巧合。正确写法是地址 +16 字节。

### 读

| 组 | 条件 | 结果 |
| --- | --- | --- |
| E | 同一 SDRAM 行内读 112 字（28 个 burst） | **112/112 全对** |
| F | 读 56 字（行内） | **56/56 全对** |
| G | 连续读 200 个 burst（跨多个 SDRAM 行） | **256/800**（前 256 字对，之后全错） |

**结论：读在同一 SDRAM 行（256 字）内完全正确，跨行必须断开。**

已按这条改 `frame_buffer`：`rd_cnt[7:0]==255` 时插 12 拍 gap（`rgap`）。

### 当前图像状态

`fb_sdram.png`：图片 640×480 完整显示在 (320,120)，黑边正确，
**81% 像素精确匹配**（57216/307200 错）。

错误模式极其规整：**每 32 像素有 6 个像素错，内容等于 +6 像素处的值**（偏 3 字）。

这个数字在所有改动下**完全不变**（改读 burst、改 occ 阈值、改跨行 gap 都不变），
说明它是确定性的字对齐问题，不是时序抖动。下一步重点：

1. 在 `tb_sdram_burst` 里复现"连续读 + 跨行 gap"能否达到 800/800，
   确认读侧的 gap 到底该多长（12 拍可能不够，tRC 是 8 拍但要算上控制器开销）；
2. 若控制器跨行读确实不可靠，就在 `frame_buffer` 里做**行对齐读**：
   只按 SDRAM 行（256 字）为单位发起读，行末强制空闲，
   并用一个 256 字的行缓冲承接，避免 FIFO 里的字顺序被跨行污染。

## 5.9 2026-10-23 晚：三条硬结论 + 一个被测方法坑

### ① 写入 100% 正确（第一次逐字证实）

在 TB 里把 SDRAM 的 153600 个字与期望图案逐字比对：

```
[res] SDRAM content match : 0/153600 wrong
```

引脚侧 `ACT=38422 / WR=38400`，38400×4 = 153600，数量吻合。
**写路径可以定案了，不用再查。**

### ② 抓帧时机是错的（此前所有图像结论都要打问号）

TB 在 `load done` 后**立刻抓帧**，而写图实际花了 8.2ms，
读侧刚开始 32ns 就被拍下。修正为「等 3 帧再抓」后：

| 指标 | 修正前 | 修正后 |
| --- | --- | --- |
| 读使能次数 | 80 | 375612 |
| fcnt 峰值 | 71 | 515 |

> 之前基于图像得出的"读跨行只有 256/800""偏移 765"等结论，
> 一半是测试方法本身的 bug（rd_q 只有 256 深却读 800 字、tag 值与 tag+3 冲突）。

### ③ 读侧错误是结构性的，不是时序

| 变量 | 取值 | 图像正确率 |
| --- | --- | --- |
| 读 burst 间隔 | 1 拍 | 81.49% |
| 同上 | 4 拍 | 81.38% |
| 同上 | 12 拍 | 81.49% |
| FIFO 水位阈值 | 512 | 81.49% |
| 同上 | 128 | 82.20% |

**间隔改 4 倍、水位改 4 倍，结果几乎不动** → 不是时序问题。

错误分布极其规整：

```
row 0..5 : 0 个错        （前 6 行完全正确）
row 6    : 96 个错
row 7+   : 120 个错 / 640 像素 = 18.75%
pattern  : 每 32 像素错 6 个（= 3 个字），起点 x=26
```

FIFO 弹出序列比对显示：**每 4 个字里第 4 个重复了前一个值**
（`i=4 got=0000 exp=0800`、`i=8 got=0800 exp=1000`）。

### ④ 判断：问题在自写 afifo 的跨时钟读指针

现象等价于「读指针每 4 次只前进 3 次」。
`afifo` 的 `rd_empty` 由 `wgray_r2` 跨时钟同步得到，写侧连续写入时它滞后，
FIFO 里实际有 4 个字而读侧只看到 3 个，第 4 次读被 `~rd_empty` 挡掉。

**下一步建议：换官方 Soft FIFO IP（IPUG012）**，它自带
`valid / rdusedw / aempty / show-ahead`，跨时钟指针是厂商验证过的，
比继续修自写 `afifo` 更省时间。

## 5.10 读带宽实测与最终定性（2026-10-24 凌晨）

### 读带宽是硬限制：7.51 M 字/s

连续 3 帧稳定运行后统计：

```
每帧实际读到 : 125,204 字
每帧需要     : 153,600 字（640x480 / 2）
缺口         : 18.5%
读带宽       : 7.51 M 字/s
60fps 需求   : 9.22 M 字/s
=> 可支持最高刷新率 48.9 fps
```

原因：控制器每处理一个 4 字读 burst，平均要 ~35 拍（ACT + READ×4 + PRE + 刷新），
`Sdr_busy` 占 28%，且 burst 之间必须留 NOP。

### 关键数据：读请求只发到需求的 89.5%

640×360（需求 115,200 字/帧，3 帧 345,600 字）实测：

```
rd_en      = 309,396     读请求次数（= 需要的 89.5%）
rf_wr      = 309,389     实际写入 FIFO
rf_rd      = 306,243     显示端消费
drop_on_full = 4         FIFO 满丢字（几乎为 0）
fcnt_max   = 1003        FIFO 曾经填满
```

**读请求少了 10.5%，而像素错 18.5%——1 个字丢了会让后面整串偏移，
所以误差被放大。**

### 控制器本身没问题

`tb_sdram_readscan` 把连续读从 256 字扩到 **2048 字（跨 8 个 SDRAM 行）**：

```
[res] SDRAM written  : 2044/2048
[res] READ back      : 2044/2048      （只差最后 4 字，是写收尾未完成）
```

**跨行读完全正确。** 读地址序列也打印过：`0,4,8,12,16,20…` 连续无跳变。

### 排除项（都已用实验否掉）

| 怀疑点 | 实验 | 结果 |
| --- | --- | --- |
| 读地址算错 | 打印 `app_rd_addr` 序列 | `0,4,8,12,16,20…` **完全连续** |
| burst 被打断 | 统计 burst 期间 busy | `busy_in_burst = 0` |
| burst 间隔不够 | gap = 1 / 4 / 12 / 16 | 正确率 81.38~81.49%，**几乎不变** |
| FIFO 水位 | 阈值 128 / 512 / 900 / 不限 | 81.41~82.20% |
| 写错误 | 逐字比对 SDRAM | **0/153600 错** |
| FIFO 溢出 | 统计 full 时仍写 | 0 次 |

### 结论：读请求数量不足，瓶颈在“FIFO 满 + busy 等待”的综合效率

地址对、数据对、FIFO 不丢，那剩下的只有 `hi / rf_dout` 的配对时序：

```verilog
rf_rd   = in_img & xr[0] & pre & ~rf_empty;   // 奇数像素弹一个字
hi     <= rf_dout[31:16];                     // 偶数像素抓高半
rgb_out = xr[0] ? hi : rf_dout[15:0];
```

FIFO 1024 深，读一次补 4 字就被 `fcnt`/`rf_full` 挡回，形成
“满 → 等显示消费 → 读 4 字 → 又满”的抖动。稳态下每秒能补的字数刚好略低于消费，
于是每帧缺 10.5%。

**下一步（按性价比）**：
1. **FIFO 加深到 2048~4096**（ERAM 还够），让读能批量预取，减少"满-停"往返；
2. **一次预取多个 burst**：FIFO 有空间时连发 4~8 个 burst（共 16~32 字），
   而不是每次只发 1 个 burst 就停；
3. 降低需求：720p30 或 480×360（见下表）。

### 分辨率建议（带宽维度）

| 图片尺寸 | 字/帧 | 60fps 需求 | 相对 7.51M 余量 |
| --- | --- | --- | --- |
| 640×480 | 153,600 | 9.22 M | **−18%** |
| 640×360 | 115,200 | 6.91 M | +9% |
| 512×384 | 98,304 | 5.90 M | +27% |
| 480×360 | 86,400 | 5.18 M | +45% |

**640×360 是 16:9，正好适配 720p，且只裁掉上下各 60 行。**

## 5.11 2026-10-24 收官：三个根因全部定位，仿真 100%

### ① 720p30 不能只加 VTOTAL，必须把像素时钟减半

一开始想用 `VTOTAL=750 -> 1500`（像素时钟仍 75MHz）来把读需求减半，这是**错的**：
读需求取决于**行内消费率** = 图片宽度/2 ÷ 行时间，和帧率无关。
VTOTAL 翻倍只是把消隐拉长，行时间一点没变，640 宽的图片仍然要
`320 字 / 22.2µs = 14.4M 字/s`。

正确做法是**像素时钟 75 -> 37.5MHz**（PLL `CLKC0_DIV 10->20`、`CLKC1_DIV 2->4`），
H/V 时序参数一个字不改（仍是 1650×750），VIC 由 16 改 4。
行时间变成 44.4µs，需求降到 `320/44.4µs = 7.2M`。

> 显示器不认 30Hz 时：`CLKC0_DIV` 改回 10、`CLKC1_DIV` 改回 2、`VIDEO_VIC` 改回 16，
> 就回到 720p60（带宽不足，图片会错位但能出图）。

### ② 16 字长 burst 被控制器否掉

为了把"每 4 字一个 gap"的开销摊薄，试过把读 burst 从 4 字加到 16 字。
结果 `burst_cycles=1288170 / busy_in_burst=1030536` —— **控制器在连续读的第 5 拍就拉高 Sdr_busy**，
busy 期间的读命令被丢弃，图像只剩 1.4% 正确。
4 字 burst 时 `busy_in_burst=0`。**这条规则是硬的，不要再试。**

### ③ 真正的元凶：`fcnt` 用"消费脉冲累加"估算，跨域后永久漂移

`frame_buffer` 原来用 `rf_rd`（像素域 26.7ns 单拍脉冲）打两拍同步到 mem 域做加减，
估算 FIFO 占用。实测 `fcnt_max = 2049 > 深度 2048` —— **已经漂到比深度还大**，
于是读侧长期停在"以为满了"的状态，FIFO 却是空的。

| 现象 | 数值 |
| --- | --- |
| `rf_full` 占空比 | 56% |
| `drop_on_full` | 763117 字 |
| 显示饥饿 `starve` | 80640 |
| 图像正确率 | 1.40% |

**修法**：`afifo` 增加 `wr_used` 输出，直接算 `写指针 - 同步过来的读指针`（格雷转二进制），
`frame_buffer` 用它限流，彻底删掉 `fcnt` 累加逻辑。

顺带做的两件事：
- 读 FIFO 深度 1024 → **2048 → 4096**（`AW=12`，14 块 M9K）。缓冲 12.8 行，
  足以跨过"burst 开销 vs 显示消费"的抖动窗口。
- `rstart` 阈值留 16 字余量（`rf_used < 4080`）。

### ④ 仿真结果

```
[res] SDRAM content match : 0/153600 wrong      <- 写入仍然 100%
[drop] drop_on_full=0 used_max=4083             <- 不丢字，FIFO 用到满
size 1280x720  图片区 307200 像素   wrong 0 = 100.00% ok
```

**640×480 @ 720p30 全链路（图案 → 写 SDRAM → 读 → 显示）逐像素 0 误差。**

### ⑤ 上板链路已接好（待上板验证）

`top_board.v` 现在包含：PLL(37.5/187.5/125/125移相) → `sdram` → `frame_buffer` →
`pattern_src`（内部彩条网格图，代替 SD 卡图源）→ `top_osd_demo`（转场/菜单）→ HDMI。

- `top_osd_demo` 新增 `USE_EXT` 参数与 `ext_rgb / raw_de / raw_x / raw_y` 端口。

## 7. 双缓冲（消除换图黑屏）为什么最终没有默认启用

### 7.1 板上现象
单缓冲（`USE_DBL=0`）：图片完全正常，换图时黑屏约 0.4s（= 读一张图的 SD 时间）。
双缓冲（`USE_DBL=1`，按行分时读写）：始终有残留黑短横线 + 固定位置竖缝。

### 7.2 定位到的三个真问题（都只在双缓冲路径出现）
1. **读 FIFO 在写窗口里被异步清零**（`aclr = wr_win_m`）
   每帧清两次 -> 窗口边界总有 0~3 个在途读数据被 `rf_wr & ~wr_win_m` 屏蔽掉，
   等于从数据流里挖掉几个字，之后整帧错位。
2. **`rd_cnt` 在写窗口里复位 + 读协议的 `pre` 标志每帧多取一个字**
   两者叠加，使"第一帧的起点"取决于加载结束落在帧内哪个位置
   （实测 `rd_cnt=74996` = 234 行），整幅画偏移。
3. **读写方向切换没有静默间隔**
   APUG011 要求读写不能同时进行；只判 `~bsend` 不够，控制器内部还有流水。

### 7.3 为什么"按行分时"这条路先天紧张
- 控制器实测上限 **7.5M 字/s**（4 字 burst ≈ 35 拍）
- 图片区读需求 **7.2M 字/s**（320 字 / 44.4µs 行）
- 余量只有 4%。任何一次方向切换、刷新、边界丢字都会直接变成画面瑕疵。

### 7.4 已做的改动（对单缓冲同样有利，保留）
- 写窗口从"帧首 25 行"改成"图片行之外，且让出图片行前 48 行"：
  `y < 97` 或 `y >= 625` 可写；`y = 97..144` 是读流归零 + 预灌区。
  这样读 FIFO 在进入图片区前有 2.1ms 把 2048 字灌满，
  **消除了原来"进图片区时 FIFO 是空的"导致的取空/偏移**。
- 读写方向切换各加 63 拍静默（`rq`/`wq`）。

### 7.5 最终定位：写侧取字握手（真凶）
前面三条都修完仍有 320 字丢失，形态很有特征：**每两个 4 字 burst 缺一个**。
加计数器后一眼看出：

```
take=153280  pop=306564   <-- 取字数是收下数的 2 倍！
drop=240     burst=38320  （期望 take=153600 / burst=38400）
```

`wvld` 原来是直接接 afifo 的 `rd_valid`，**只有 1 拍宽**。只要这一拍
`can_accept=0`（正在发 burst / `bgap` 期间 / 组已满），这个字就永远丢了，
而下一拍 `~wvld` 又会再取一次 —— 一次正好丢 4 个字，形成"隔一个 burst 缺一个"。

单缓冲时写窗口全开、握手几乎不撞车，所以这个问题一直没暴露。

**修法**：afifo 的 `rd_data` 在下次 `rd_en` 之前一直保持，所以"待取字"可以是电平：
- `wpend`：有一个待取字，直到被组装器收下/丢弃才清（电平有效）
- `wfly`：已发 `rd_en`、数据未回（防止两拍内连发）
- `wf_rd` 改成**组合**判"槽位空"：`wr_win_m & ~wf_empty & ~wpend & ~wfly`

### 7.6 当前结论（2026-10-25 更新）
- **`USE_DBL = 1` 已启用为默认**，且是在**读写同 bank 的最坏条件**下验证的：
  ```
  [wr]  take=153600  pop=153600  drop=0  tail=0  burst=38400
  [res] SDRAM 0/153600 错
  图像  307200 像素 0 错 = 100%
  ```
- 单缓冲（`USE_DBL = 0`）回归同样 100%：SDRAM 0/153600 错、图像 0 错。
- 状态机单元测试：CLEAR 3803 拍/次 × 75 次无死锁，PASS。
- 换 bank 的安全性：`wr_idle` 现在包含 `~wvld & ~wfly`，
  保证不会有"已取未写"的字落到新 bank；换 bank 只在非图片行发生。
- 若上板仍见异常，把 `USE_DBL` 改回 0 即退回单缓冲（换图黑约 0.4s，路径最短）。

## 8. 转场：双 bank 整幅推入（无黑场）

### 8.1 为什么不能用淡入淡出
淡入必然经过"全黑"那一帧，用户明确不能接受中间黑一下。
而真正的交叉淡化需要同一像素同时读旧图和新图（两个地址），
单读口带宽只有 7.5M 字/s（读需求已占 88%），加不起。

### 8.2 方案：按字索引分界的 bank 选择
`frame_buffer` 增加 `rd_bank_new` / `rd_wipe`：
```
bank_eff = (rd_cnt < rd_wipe) ? rd_bank : rd_bank_new
```
- 正常显示：`rd_wipe = 153600`，全部读 `rd_bank`
- 转场：每帧把 `rd_wipe` 减 15360（= 48 行），10 帧推完
  -> 新图从下往上推入，两张图同屏共存，**没有一个全黑帧**
- 分界恒为 4 字对齐（153600、15360、320 都是 4 的倍数），
  4 字 burst 绝不会跨 bank，控制器不会读到错位数据

### 8.3 关键约束：分界只能在帧首更新
`rd_cnt` 在写窗口里被复位，图片行开始时恒为 0，
所以在 `frame_top` 更新分界，本帧的读全部按新分界进行，不会出现半帧撕裂。

### 8.4 验证
`sim/tb_frame_win.v` 增加地址检查：设 `rd_wipe=76800`，
逐拍核对 `app_rd_addr == rd_cnt*4 + (跨分界 ? 614400 : 0)`：
```
[wipe] 检查 155636 拍：上半 78836、下半 76800，地址错 0   -> PASS
[wr]   take=153600 pop=153600 drop=0 burst=38400
```
