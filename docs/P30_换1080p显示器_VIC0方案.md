# P30　1080p 显示器兼容：720p50 + AVI 声明 VIC = 0

## 1. 这一步在验证什么

30Hz（VIC 62）上板结果：**仍然"不支持"**。这条信息很有价值：

- 12:38 版：AVI 写 VIC 4（720p60），实测 30Hz → "不支持"
- 17:25 版：AVI 写 VIC 62（720p30），实测 30.3Hz → **还是"不支持"**

两次 AVI 不同、结论相同，说明显示器**不是**被 AVI 误导，而是**自己测到了 30Hz
并把这一档拒掉**。多数显示器的垂直扫描范围是 50~75Hz（VESA），30Hz 落在范围外，
报"不支持"完全合理。同时也说明：**TMDS 在 187.5MHz 串行时钟下锁得住**，
同步建立没问题。

于是只剩一条路：把刷新率提到 50Hz 以上。而 50Hz 那次报的是 **"无信号"**
（连同步都没建），所以这次要同时改两件事做判别：

| 变量 | 17:07 版 | 本版 |
|---|---|---|
| HTOTAL / 行总长 | 1342（非标准） | 1342（不变，50MHz 下 50Hz 只能是这个量级） |
| AVI VIC | 19（= 标准 720p50，对应 1980 行总长） | **0（不声明标准模式）** |

VIC 19 的问题是"自相矛盾"：AVI 说"我是标准 720p50（1980 行总长）"，
实际给的是 1342。显示器核对不上，干脆判定无信号。VIC 0 的语义是
**"没有对应的标准模式"**，显示器只能退回按实测的 H/V 频率判断：
37.26kHz / 49.79Hz 都在同步范围内，非标准行总长就不再被拒。

## 3. 顺带修掉一个时序违例（−0.168ns）

50MHz 下布线后 `clk_pix` 差 0.168ns，违规路径是：

```
u_core/xd1_reg[5] -> u_meter/sx_r_reg
   x → cdx(x-640) → ax(取绝对值再加) → 乘法 → 加法 → rsq_r
   14 级逻辑，含 1 个 MULT18 和 4 个 ADDER
```

也就是圆形频谱的 `rsq = ax² + ay²`，把"坐标减法 + 取绝对值 + 平方 + 求和"
串在了一拍里。改成两级：

```verilog
// 原来：rsq_r <= (ax * ax) + (ay * ay);          // ax/ay 是当拍的组合值
rsq_r <= (ax_r * ax_r) + (ay_r * ay_r);            // 用上一拍已寄存的 ax_r/ay_r
cbin_r <= cbin;                                    // 扇区索引同步打一拍，保持对齐
```

`tb_meter_style` 重渲染对照：新旧两版圆的形状完全一致，差异只有 6780 个像素
（整幅 1 像素位移带来的边缘差），即功能等价。`run_audio` 的 5 条失败断言
在改动前后**数量相同**，都是配色改版时留下的旧断言。

### 顺带修掉的第二处违例（clk_mem −0.973ns）

读优先门控 `wr_ok` 的输入是从写域看读指针（`rgray` 同步过来）算出的水位，
直接进"写突发启动"条件后串成

```
读指针跨时钟 -> rf_used -> wr_ok -> 突发启动 -> bi（125MHz，8.69ns）
```

门控只是水位粗判，把结果寄存一拍即可，代价 8ns，无功能影响。

## 5. 上板判读（三种结果分别意味着什么）

1. **能显示** → 问题解决。可以把该模式记下来，以后就用这个码流；
   画面会被显示器缩放填满 16:9 屏幕（1280×720 是标准比例，不会变形）。
2. **仍"无信号"** → 基本可以判定是 **250MHz 串行时钟** 的问题
   （VIC 0 已经排除了 AVI 矛盾这条）。请把 720p30 码流插回 2K 屏确认它仍正常，
   然后在 50Hz 这条路上就得换实现：把像素时钟降回 37.5MHz（串行 187.5MHz，
   已验证），用 800×600@60 输出 —— 37.5MHz ÷ (1025×610) ≈ 60.0Hz，
   行频 36.6kHz，两个频率都在显示器范围内。
   代价：4:3，需要改帧缓存读侧的缩放比（960×540 → 800×600）与菜单坐标。
3. **显示但画面撕裂/雪花** → 时序或读通路余量不足，把 `clk_pix` 余量做厚再看。
