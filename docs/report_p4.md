> 图 3 标出了三个时钟域与两处跨域点。数据从 25 MHz 侧进入、以 125 MHz 写入 SDRAM、再以 37.5 MHz 读出，每一处跨越都由异步 FIFO 承担，且写入侧与读出侧的复位语义严格分离。

**（4）BMP 解码与缩放适配。** `bmp_decode` 解析 14 字节文件头与 40 字节信息头，取得位深、压缩方式、图像宽高与数据偏移，然后按"行倒序、字节对齐到 4"的规则逐行取点。支持的位深包括 1/4/8 bit（带调色板）、24 bit（BGR）与 32 bit（BGRA，忽略 alpha），内部统一转成 RGB565 输出，同时给出该像素在屏幕上的坐标，供帧缓存计算写入地址。

`bmp_scale` 负责把任意源尺寸映射到 960×540。映射不是简单比例缩放，而是分三种情况：源尺寸恰好是目标尺寸时直通；源尺寸是目标的整数倍时按整数步长抽取；其余情况按双线性插值。其中"4:3 抽取"是本作品的关键设计：1280×720 显示区对应 960×540 帧缓存，需要每 4 个像素取 3 个，实现时用计数器精确控制抽取相位（取第 0、1、3 个），而不是用 `x * 3 / 4` 之类的乘除近似——后者的累积误差会让画面右侧出现细微的错位带。

这里还有一个曾经困扰很久的"零散错位点"问题：早期 `bmp_scale` 输出时没有检查下游是否接受，帧缓存 FIFO 满的瞬间被静默丢弃一个像素，整行因此左移一格。修复办法是给输出加一级保持寄存器与 `o_busy` 反压信号，让"丢不起的像素"根本不会被产生。

**（5）帧缓存与写通路（本作品的核心改造）。** `frame_buffer` 把像素组装成 32 位字、每 4 个字发起一次 SDRAM 突发写，读出侧按行预取到 1024 深的行 FIFO，再按 4:3 抽取送显示。双缓冲 A/B 两块，写一块读一块，帧末乒乓切换，因此换图过程不会撕裂。

工程上最关键的一处改造在这里。原始设计中，写 FIFO 的出队使能绑在"帧首窗口"信号上：

旧写法的问题在于把两件事写进了同一个条件：

`assign wf_rd = wr_win_m & ~wf_empty & ~a_vld & ~wfly;` —— 写 FIFO 出队使能；

`assign wr_win_m = load_mode | (y < 16);` —— 写窗口，只在每帧帧首 16 行打开。

含义是"写 FIFO 只在每帧帧首的 16 行（750 行的 2.1%）里排空"。这在播放静态画面时没有问题，因为写入量本来就是每帧一次；但读图时数据源是持续灌入的（一个 4 KB 簇约 1365 像素），FIFO 一到 64 深就把读卡器挡在 `S_GAP` 状态，只能等下一帧的消隐期——一张 960×540 的图需要等上千帧，于是用户看到的是"进度条 0→99 反复、一次切图接近 30 s"。

第一次尝试是"FIFO 一堵就把整帧写窗口打开"，速度确实回到了 1.3 s，但画面在切图过程中花屏。原因随后查明：`wr_win_m` 在读侧并不表示"暂停"，而是**整段复位**——它同时接到读 FIFO 的 `aclr` 和行游标（`rcol / rrow / rout`）的清零端。在屏幕扫描中途把它拉高，读 FIFO 被清空、行游标归零，画面必然撕裂。

正确的做法是把被同一个信号绑死的两件事拆开：

`assign wf_rd = ~wf_empty & ~a_vld & ~wfly;` —— 出队：任意时刻都允许；

写突发的启动条件同样去掉 `wr_win_m`，保留原来的 `bfull && rq == 63 && ~rburst`。

读侧的复位与预灌逻辑一行未动（仍只在帧首窗口），只把"写 FIFO 出队 / 发起突发"这一半放开。安全性由带宽预算保证：写突发被 `wq` 限速为每 64 拍最多 4 字（约 7.8 M 字/s），而读图时源只有约 0.15 M 字/s；读侧仅占约 9% 的 SDRAM 带宽，1024 深行 FIFO 有约 73 µs 余量，足以吸收一次突发带来的几十拍延迟。

改造后的实测：单张切图 1.3 s（清屏 35 ms + 读图约 1.0 s + 淡入 270 ms），全帧仿真中 SDRAM 259 200 字与显示 921 600 像素均零错误，读 FIFO 峰值 1027/2048，丢字与饥饿计数均为 0。

还有一处只有上板才会暴露的缺陷：清屏与读图产生的写突发会长时间占住 SDRAM，而读侧是按**固定时隙**取数的（等写计数走到 63 且控制器不忙）。写繁忙时这个时隙会被吞掉，下一次要再等 64 拍；读 FIFO 只有约两行的余量，连丢几个时隙就饿死，表现为"按下切屏那一瞬间画面撕裂"。由于只有清屏那二三十毫秒是满带宽写，平时完全看不出来。为此新建 `tb_tear` 专项测试台复现（后台整帧写入期间 77 万像素全部出错、饥饿 28.9 万次），并给写突发加了一道水位门控：读 FIFO 低于 768 时写侧暂停，首张与单缓冲时旁路。修复后同一场景 79.4 万像素零错、零饥饿，换块后 92.2 万像素零错，读图耗时不变。

**（6）超时自愈与状态机。** 图片载入由顶层五态状态机驱动（等待 → 清屏 → 切 bank → 读图 → 显示），每个等待都有超时退路，失败后自动重挂载、重读一次。这一机制是"广告牌能长期无人值守运行"的保证。

> 图 4 上半部分为顶层五态，下半部分为读卡器内部状态。两层的超时是串联的：读卡器内部先按 21 ms 级别处理局部异常，顶层的 3.4 s 只作为最后兜底。

**（7）转场与图层合成。** `transition` 模块在两张图之间提供四种过渡：FADE（按帧计数的透明度插值）、SLIDE（新图从右侧推入）、WIPE（竖直擦除边界右移）、CUT（直接切换）。四种效果共用同一套"当前帧进度 → 混合系数"的接口，因此菜单里换效果不影响上层时序。

**（8）OSD 菜单。** `osd_menu` 是纯像素域、纯坐标实时生成的字符界面：不读帧缓存、不占 SDRAM 带宽，只根据当前扫描坐标判断"这一点属于哪个面板、哪一行、哪个字符的哪一位"，再用字模 ROM 取出点阵。内部是四级流水（区域判定 → 地址计算 → 字模取位 → 合成），输出比输入坐标晚 3 个像素，与视频流水线严格对齐。

菜单共四页：设置页（图片入口、亮度、对比度、缩放模式、音量、频谱开关、字幕开关）、音乐列表页（关 / 内置音阶 / 卡上曲目）、图片子菜单（轮播开关、切屏效果）、频谱子菜单（样式选择）。打开、关闭、进出二级菜单都有淡入淡出：新增一个帧域的透明度电平 `mfade`（0~8，每帧 ±1，约 0.27 s 走完），渲染条件从"菜单是否打开"改为"菜单是否打开或尚未淡尽"，因此关闭时面板会继续被画出来，直到淡到全透明；换页则在 `mfade` 归零的那一帧完成，做到"全黑换页"，不会出现半透明时内容突然跳变。

**（9）音频播放与可视化。** `wav_player` 定位 WAV 文件的 `data` 块后顺序读取，按 48 kHz 节拍从 FIFO 取一个 16 bit 采样，乘以音量系数后扩展为 24 bit 送入 HDMI 数据岛。这里有一个容易被忽略的坑：若输入是立体声文件（每帧 L、R 两个 16 bit 字），而播放器按"每节拍取一个字"的方式取样，就会一帧占两拍，表现为"时长翻倍、音调低八度"。解决办法是在 PC 侧把音频转成单声道，或在播放器里按声道数跳采样——本作品采用前者，并编写了纯 Python 的转换脚本，不依赖任何第三方库。

`audio_meter` 用 Goertzel 算法把时域采样变换到 32 个频点，每个频点独立计算能量并做峰值保持与缓慢回落。显示有两种样式：条形模式为 32 根竖条；圆形模式为从中心向外辐射的环形条带，判定式为"平方半径差小于阈值"，即

`rdiff = dx*dx + dy*dy - 8100;`（减去内圈半径的平方），当 `rdiff >= 0` 且 `rdiff < (level << 8)` 时点亮。

必须用平方半径比较而不是 `max(|dx|,|dy|)` 或 `(max+min)/2` 之类的近似——后者画出来是八边形而不是圆。这一段组合逻辑曾经长到把 clk_pix 的余量压到 +0.07 ns，最终通过三级流水（把坐标打拍到 `xd1` 再运算）恢复到 +2.1 ns。

**（10）按键与导航。** `key_ctrl` 完成同步、20 ms 消抖、单击与长按（400 ms 后 100 ms 连发）识别；`nav_ctrl` 负责"菜单态"与"播放态"两套语义：菜单态下上下键移动高亮、确认键改值；播放态下上下键切图、菜单键开设置、列表键开音乐列表。轮播计时独立于按键，且只有在轮播开关打开时才累加——早期版本把两件事耦合在一起，导致"关掉轮播后切图间隔依然生效"以及"改一次间隔就立刻切一张图"。

**（11）现场诊断。** 六位数码管在正常态显示"加载次数 | 出错状态 | 图片数 | 音乐数"，加载过程中前两位变为 00~99 的进度。第二位在出错时记录读卡器停在哪个状态（1=TBL、2=CMD、3=WT、4=RCV、5=GAP、6=F0、7=F1、8=F2），相当于把状态机"搬"到了面板上。这套诊断在本项目的调试中起到了决定性作用：面板上出现 `2 0 4 9 1 1` 时，可以立刻判断"本次切图触发了 2 次加载、只按了 1 次键、整次耗时不足 0.9 s"，从而排除按键连发与硬超时，直接锁定到读卡器毫秒级报错。
