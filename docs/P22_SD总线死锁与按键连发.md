# P22 一次切图 30 秒的真因：SD 总线死锁 + 按键连发

> 2026-10-28 20:55

## 1. 现象

按下「下一张」后，数码管进度 **0→99 完整重来 3~4 次**才换一张图，
总耗时接近 **30 秒**。

## 2. 数字先对上

- 进度的 tick = `ld_wdog[19]` 上升沿 = 2²⁰ 拍 @37.5 MHz = **27.96 ms**
- 一次 0→99 = 99 × 27.96 ms = **2.77 s**
- 每次加载失败要等 `ld_wdog` 的 28 位看门狗 = **7.16 s**
- 4 次 × 7.16 s = **28.6 s ≈ 30 s** ✓

也就是说：**每一次加载都卡死了，一直等到看门狗超时才放弃，然后又重来一次。**
（正常加载只需要 1.3 s，进度只会走到 47 左右就出图，根本到不了 99。）

## 3. 根因一：`sd_read` 没有任何超时

```verilog
4'd1 : begin                      // 发完 CMD17，等卡响应
    if (res_en) rd_ctrl_cnt <= rd_ctrl_cnt + 1;
end
4'd2 : begin                      // 收 512 字节
    if (rx_finish_en) rd_ctrl_cnt <= rd_ctrl_cnt + 1;
end
```

两个阶段**都没有退路**：

| 异常 | 后果 |
|---|---|
| 卡没回 CMD17 响应 | `rd_busy` 永不落下 |
| SPI 丢了字节，收不满 512 | `rx_finish_en` 永不来，`rd_busy` 永不落下 |

`rd_busy` 一卡住，仲裁器 `idle = ~active & ~s_busy` 恒为 0 →
**图片读取器的请求永远得不到授权**，它在 `S_WT` 里死等 `rd_busy` →
只能等上层 7.16 s 看门狗。

## 4. 根因二：切图按键吃到了「长按连发」

`key_ctrl` 有长按连发（500 ms 后每 100 ms 一次 `rep`），菜单里的上下移动靠它翻列表。
但 `nav_next/nav_prev` 原来也接的是 `press|rep`：

```verilog
.nav_next(nav_next)      // 内部 = ~open & (press|rep)
```

**按一下稍微按久一点（0.8~1.2 s），就会连发 3~4 次 `nav_next`**，
每一次都会把刚启动的加载打断、`ld_wdog` 归零、进度回 0 ——
所以看起来就是「进度 0→99 反复重来」。
（反过来也解释了更早的「有时等一会就会切屏」：挂起的按键在加载完成后补执行。）

## 5. 修了什么

| 位置 | 改动 | 作用 |
|---|---|---|
| `sd_read` | 等响应、收数据各加 16 位超时（2.6 ms） | **总线永不死锁**，最坏 2.6 ms 就退出 |
| `sd_bmp_reader` | `S_WT` 等不到 `rd_busy` → 撤请求重发（最多 4 次） | 请求被仲裁器漏掉时能自愈 |
| `sd_bmp_reader` | `S_RCV` 收不满 256 字 → **直接判整张失败**（不重试） | 字节流已错位，重试只会让后面全部偏移 |
| `sd_bmp_reader` | 新增 `err` 输出 | 失败时上层能知道 |
| `top_board` | 收到 `err` → **保留上一张继续显示**，立刻退出加载 | 不再黑屏/花屏，也不再等 3 秒 |
| `top_board` | 加载看门狗 7.16 s → **3.4 s** | 兜底更快 |
| `top_top_osd_demo` | `nav_next/nav_prev` 改成只用 `press`（菜单仍用 `press\|rep`） | 长按不再连发切图 |
| `top_board` | `media_alert` 增加 `scan_err / mnt_err` | 扫描/挂载出错也提示，不再纯黑屏 |

## 6. 仿真验证（新增故障注入）

给 `tb_fat_chain` 加了三个注入开关（`+FAULT=n` / `+HALF=n` / `+FAULT_ALL=1`），
直接对真实的 `sd_arb + fat_mnt + fat_scan + fat_tbl + sd_bmp_reader` 打故障。

### 6.1 单次「卡不响应」（模拟丢 CMD17 响应）

```
[inj] 第 15 次传输被丢弃（sec=2114）
[img 0] bytes=230912 bad=0        ← 重试后仍然读完整、逐字节 0 错
RESULT: PASS
```

**2.6 ms 超时 → 重发 → 成功**，图片完全正确。

### 6.2 单次「半截数据」（模拟 SPI 丢字节）

修复前：

```
[img 0] bytes=231112 bad=223638   ← 多出 200 字节，22 万个像素错位
```

修复后：

```
[img 0] bytes=5832   bad=0        ← 检测到中断立刻停，已输出的部分全对
```

**不再产出错位数据**，由上层保留旧图。

### 6.3 常规回归

| 项目 | 结果 |
|---|---|
| `run_fat`（无故障） | 图片 230912 / 57856 字节 **0 错**、WAV 3000 采样 0 错 → PASS |
| `run_osd` | PASS |
| `run_nav` | PASS |
| 全工程编译 | Errors 0 |

## 8. 上板后应该看到什么

| 情况 | 表现 |
|---|---|
| 一切正常 | 按一下 → 进度 0 涨到 **40 多**就淡入出图（约 1.3 s） |
| 某扇区偶发失败 | 进度走到某个数 → 直接**保留旧图**（不黑、不花）→ 再按一次即可 |
| 卡彻底不通 | 3.4 s 内退出来，底部显示 `NO IMAGE`，数码管 `F/mnt_err` |

**再也不会出现「0→99 反复重来、一次 30 秒」。**

## 9. 还没解决的：为什么会丢数据

这次修的是「丢了之后别卡死」，并没有让 SD 通信本身更可靠。
真机上偶发丢响应/丢字节，常见原因：

1. **杜邦线太长 / 接触不良**（SD_CLK 25 MHz 对走线敏感）→ 换短线、插紧
2. 卡座弹片氧化 → 重新插拔几次
3. 卡本身在某段区域读不稳（尤其廉价卡）
4. 板子 SD_CLK 与其它信号串扰

如果换了这版之后**仍然经常看到「保留旧图」**，把数码管的 `F` 那一位报上来，
就能定位是挂载、扫描还是读图出的问题。

## 10. 还没做的健壮性（可选）

`fat_mnt` / `fat_scan` 的等待循环仍是「死等」，靠 `top_board` 的
`sd_reinit`（`LD_WAIT` 停 2.7 s 后整段复位重试，最多 3 次）兜底。
如果以后发现开机阶段卡住，可以照 `sd_bmp_reader` 的写法给它们也加扇区级超时。
