# P11 花屏 / 音频条 / 爆音 三个问题的定性与修复（2026-10-26）

> 这一版上板：花屏无法显示、音频条只在图片右下角一小块、音乐有尖锐爆音。
> 三个问题都有明确根因，其中两个是**上一版自己引入的真 bug**，一个是
> **一直存在但从来没被看见的时序问题**。

---

## 1. 音频条只显示一小块：顶层把 NBAR 写成 80，模块内部按 127 算索引

`audio_meter.v` 改成 128 列时，模块内部是这样算列号的：

```verilog
wire [6:0] bi = 7'd127 - dx[9:3];      // 127 写死
```

而 `top_osd_demo.v` 里的实例化**没有跟着改**：

```verilog
audio_meter #(.X0(320), .Y0(468), .BARW(8), .NBAR(80), .MAXH(112)) u_meter (...)
```

于是 `bi` 会算到 48..127，去读一个只有 **80 项**的 `bars[]` —— 越界读。
综合后取到的是无效数据，屏幕上看得到的只是其中一部分（因为绘制区也只有
80×8 = 640 像素宽，正好压在图片下部），于是就成了"音频条只在图片右下角"。

**修法**：
- 索引不再写死：`bi = (NBAR-1) - cidx`，并加越界钳位；
- 顶层实例化改成 `.X0(128), .NBAR(128)` → 128×8 = **1024 宽**，铺满画面中段；
- 新增 `sim/tb_meter_full.v`：**从顶层**核对电平条（打印实际生效的
  `NBAR/X0/XW`，并在 y=579 那行扫出点亮范围），专门防这类"单测永远发现不了"的
  参数不一致。

验证输出：

```
[info] 顶层生效参数: NBAR=128 X0=128 Y0=468 BARW=8 XW=1024
[info] y=579 行点亮范围: x = 128 .. 1132（期望 128..1151）
[ok] 柱子铺满 x=128..1132
[PASS] 顶层电平条几何正确
```

（`sim/meter_full.png` 是这一条 TB 导出的实际渲染：128 根柱子横跨整幅画面，
顶部红→底部紫 14 级渐变。）

## 2. 尖锐爆音：SD 读回的"扇区"会多给/少给字，接收侧字节流错位

`sdcard` 一次读返回 512 字节 = **256 个 16bit 字**。上一版 `sd_arb` 是靠
"盯 `busy` 的上升/下降沿"判断一次传输的开始与结束，再把 `s_val` 直接门控给
owner。实板上 `rd_val_en` 的拍数/相位与仿真模型并不完全一致（CRC 尾字、
切主瞬间的残留拍），**一旦多给或少给一个字，接收侧就从此错位半个采样**：

- 图片侧错位 → BMP 解码错位 → **花屏**
- 音频侧错位 → 采样值整体错位 → **尖锐的沙沙/爆音**

**重写 `sd_arb.v`**：由仲裁器**自己数满 256 个字**再释放，一次授权正好放行
256 字，不多不少。实现上不依赖 busy 边沿：

```
授权 -> active=1（对客户端拉高 busy）
     -> 此后 s_val 来一个放行一个，数到 256 -> wend=1
     -> 等 busy 落下（早落下也不影响）-> 释放
```

另加两个看门狗（等数据超 16K 拍、等 busy 超时），任何异常都不会再把总线锁死
（上一版 `active` 卡在 15、音频图片双双饿死就是这类问题）。

配套修的两处：

| 位置 | 问题 | 后果 |
|---|---|---|
| `wav_player.fifo_wr` | 没有 `& bsync` | 上一扇区尾巴/CRC、切主残留的字被写进 FIFO → 整条流错位 |
| `wav_player.s_req` | 第 256 字后才撤 | 那一拍仲裁器已空闲，可能多起一次传输（重复扇区） |

验证（`sim/tb_wav.v`，假 SD 按 `sd_read` 时序吐真实 WAV 字节，喂
`音乐资源/2_T2.wav`）：

```
[ok] 采样率 47900 Hz（10ms 内 479 个）
[info] 比对 5479 个采样，错 0 个
[ok] 扇区地址连续（首扇区 0）
[PASS]
```

## 3. 花屏：TD 时序报告里 125MHz 域本来就不满足（顺手修掉两条长路径）

`prj/yuanshen_hdmi_Runs/phy_1/yuanshen_hdmi_pr.timing`（用户这次综合的结果）：

| 时钟 | 约束 | 实测 Fmax | 最差 slack | 违例端点 |
|---|---|---|---|---|
| clk_pix 37.5MHz | 26.7ns | 49.9MHz | +6.6ns | 0 |
| **clk_mem 125MHz** | 8.0ns | **82.5MHz** | **-4.12ns** | **135** |

最差路径：`u_fb/u_wfifo`（写 FIFO 的 BRAM 输出）→ 一串加法器（**含一个乘法器**）
→ `u_fb/baddr`（SDRAM 写地址）。也就是说 **SDRAM 写地址可能被写错** ——
这正好对应"花屏 / 局部错位"。

### 3.1 去掉 125MHz 路上的乘法器

```verilog
// 原来
wire [17:0] row_base = dy * IW9;          // IW9 = 320，综合成 18x18 乘法器
// 现在（IW=320=256+64，纯移位加法；其它宽度自动退回乘法）
generate
    if (IW == 320) begin : g_row_sh
        assign row_base = ({9'd0, dy} << 8) + ({9'd0, dy} << 6);
    end else begin : g_row_mul
        assign row_base = dy * IW9;
    end
endgenerate
```

### 3.2 读 FIFO 占用量打一拍再进水位比较

`rf_used` 是"跨时钟域同步 + 格雷转二进制"算出来的，链很长，却被直接用来做
`rstart` 的水位比较，再经 `rd_go` 进 SDRAM 控制器的命令译码。占用量的变化
是"每几个周期才 1 个字"，打一拍完全不影响判断（阈值 2032 / 深度 2048 本来
就留了 16 字余量）。

### 3.3 效果（用 TD 命令行重跑综合，逐次对比）

| 版本 | clk_mem Fmax | 最差 slack |
|---|---|---|
| 修改前 | 82.5MHz | -4.12ns |
| 去掉乘法器 | 97.9MHz | -2.22ns |
| 再给 `rf_used` 打一拍 | **106.2MHz** | **-1.42ns** |

> 仍然差 1.4ns（剩下的最差路径是"写 FIFO 的 BRAM 输出 → 6 个加法器 → baddr"，
> 其中 3.2ns 是 BRAM 自身的 clk2q）。要彻底解决需要把写侧组装器整个后移一拍
> （加 skid buffer），属于对历史 bug 高发模块的大改，这一版先不动。
> 如果上板仍偶发花屏，下一步就做这件事。

## 6. 上板顺序建议（便于定位）

1. **先只验图片**：菜单 `MUS` 设 `OFF`（不读音乐，SD 总线全给图片）。
   正常应稳稳出图、无花屏。若这一步就花屏，说明是 125MHz 那条路径（见 §3.3）。
2. **再验内置音阶**：`MUS = GEN`，应听到随图片变调的 8 音符循环，柱子满宽跳动。
3. **最后验 WAV**：`MUS = T1/T2`，应是干净的音乐，无爆音/沙沙声。

## 7. 第二轮上板反馈（黑屏 / 音频条已好 / 爆音仍在 / 菜单冲突）

### 7.1 黑屏：仲裁器"自己数 256 字才释放"是错的（本版已回退）

上一版把 `sd_arb` 改成"数满 256 个字才释放总线"，想法是保证一扇区不多不少。
但客户端的 `rd_start_en` 是**看到 busy 才撤**的，两边的"一次传输结束条件"
不一致，结果：

```
仲裁器：active 一直等 256 字
客户端：已经在收第 N 个字，busy 却先落了 -> 停在 S_RCV 再也不动
        -> BMP 数据一个字节都进不了帧缓存 -> 黑屏
```

这正是上板现象（图黑、菜单/电平条正常，因为它们的像素通路不依赖 SD）。

**已回退成"真实 busy 落下即释放"**（就是曾经显示正常的那个语义），
只保留两个看门狗（等 busy 16 拍超时、active 卡住 20ms 强制释放）。

为了以后不再犯，新增 **`sim/tb_sd_chain.v`**：假 SD 控制器按 `sd_read.v`
的真实时序（命令 150 拍、每 4 拍一个单拍 val、CRC 收尾 13 拍）驱动
`sd_arb + sd_bmp_reader`，并让音频客户端在中途插队抢总线：

```
[info] 图片: 收 4096 字节，错 0；音频: 收 1024 字，错 0
[ok] 图片 8 个扇区逐字节正确
[ok] 音频在图片读期间插队，数据没有串
[PASS] sd_arb + sd_bmp_reader 联调通过
```

> 这条链以前从来没被单独仿真过 —— 这就是它能在两次上板里反复出问题的原因。

### 7.2 菜单冲突：设置页第 5 行还挂着 MUS

设置页那一行的**标签**还是 `MUS`，但按下去改的是"自动轮播"，看起来就像
设置菜单里还有一个没用的音乐项、和音乐列表打架。

现在这一行是 **`AUT` / ON/OFF**（自动轮播），音乐列表只在 KEY3 那一页：
`OFF / GEN / T1 / T2`。

### 7.3 T1/T2 爆音：先把"卡上的镜像"排除掉

现象：`GEN`（内置音阶）完全正常，`T1/T2` 是尖锐噪声、听不出原曲。
音频通路在仿真里喂**真实歌曲文件**是 5479 采样 0 错，说明数字通路没问题，
那么最可能是**卡上的镜像和 RTL 的参数对不上**：

| 镜像 | 大小 | 音乐区起始扇区 |
|---|---|---|
| 早期（8 图 + 4 首演示曲） | 39.6 MB | 45312 |
| 当前（3 图 + T1/T2） | 57.1 MB | **18272** |

如果卡还是早期那份，读扇区 18272 拿到的是**图片像素**，当 PCM 播出去就是
一段段的尖锐噪声 —— 而图片照样显示正常（前 3 张图在两种镜像里的扇区一样），
这与现象完全吻合。

**因此加了一道硬保护 + 自检**：

- `wav_player` 校验曲目首扇区的头两个字是否为 `"RI"` `"FF"`，
  不是就**不放声**（宁可静音，也不把图片当音乐播）；
- 同时把结果送到数码管：**最高位显示 `F`** = 音乐区头校验失败（卡/参数不匹配）。

所以这一版上板只要看数码管：
- 选 `T1` 时显示 `F..` -> 卡没按当前镜像重写（重跑 `tools/write_sd.bat`）
- 显示正常数字且有音乐 -> 卡是对的，问题在别处（再往下查采样率/HDMI 音频）

## 8. 第三轮上板反馈（T1/T2 无声 + 数码管 F、彩条不平移）

### 8.1 数码管 F = 音乐区头校验失败，说明卡上的内容对不上 RTL

上板显示 `F70000`，最高位 `F` 就是 `trk_bad`。而仿真里喂**真实 WAV**
时 `trk_bad=0`（`tb_wav` 已加断言），说明校验逻辑本身没问题：

```
[info] trk_bad=0（好卡应为 0）
[PASS] wav_player 全部用例通过
```

所以是**卡上的扇区 18272 开头不是 "RIFF"** —— 也就是卡里还是旧的镜像。
这解释了两件事：图片照常（前 3 张图在两种镜像里扇区相同），
而音乐读到的是图片像素。

**新增 PC 端核对**：`tools/verify_sd.bat` 现在除了整盘 SHA256 比对、逐张
BMP 头检查，还会把镜像里所有**扇区对齐的 `RIFF/WAVE`** 找出来，
再把卡上同一位置的头 4 字节读出来对照：

```
music slots in image: 2
  [M1] @sector 18272  card='RIFF'  263.0 s  OK
  [M2] @sector 67600  card='RIFF'  170.7 s  OK
```

只要出现 `BAD - RTL 会静音并显示 F`，就重跑 `tools/write_sd.bat`（管理员）。

### 8.2 彩条"只平移到屏幕中间、左半一直是峰值"

上一版 `audio_meter` 用 **128 个寄存器每帧整列移位**：

```verilog
for (i = NBAR-1; i > 0; i = i - 1) bars[i] <= bars[i-1];
```

这种写法在综合时极易被映射成 SRL/移位链，而**并行随机读只认到部分抽头**，
表现正好是"右半在动、左半停在初值（填满时的峰值）"。

改成**环形缓冲 + 写指针**，不做任何整体移位：

```verilog
hist[wp] <= peak;  wp <= wp + 1;            // 每帧只写 1 个单元
raddr = wp + cidx;                          // 第 c 列（0=最左，127=最右）
lv    = hist[raddr];                        // c=127 -> wp-1 -> 最新，放最右边
```

同时"铺满"也不再是 128 路并行写，而是一个 128 拍的小填充（出声瞬间触发，
约 3.4µs 完成）：静音 45 帧以上再来声音就整幅铺满，不会出现"从右边慢慢长"。

`sim/tb_meter_full.v` 也跟着改成灌 `hist` + `wp`，仍然校验：
铺满 x=128..1140、左右映射正确（左=最老=矮、右=最新=高）。
