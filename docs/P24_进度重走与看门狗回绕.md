# P24 进度条重走（0→99 反复）根因：28 位看门狗回绕 + 超时判定只成立 1 拍

> 2026-10-28 22:00
> 上板现象：一次切图进度 `00→99` 完整重走 3~4 次，实际耗时接近 30 秒；
> 加载完后数码管 `1 0 4 9 0 8`（= 只加载了 1 次、0 丢字、4 张图、SHOW、
> 挂载完、扫描完）。**加载次数是 1，说明不是"反复切图/反复加载"，
> 是同一个加载过程里进度显示被清零重走了。**

## 1. 根因：一个计数器干了三件事

旧代码里 `ld_wdog` 同时被当成

1. 进度节拍的时基（`prog_tick = ld_wdog[19]`），
2. 加载超时（`ld_wdog == 28'h7FFFFF0`），
3. 进度清零条件（`if (sc_clr || ld_wdog == 28'd0) prog <= 0`）。

三件事互相污染，链条是这样的：

```
LD_LOAD 里： if (!rdr_done_p) ld_wdog <= ld_wdog + 1;     // 只在没人回答时累加
超时判定：   ld_wdog == 28'h7FFFFF0                        // 只成立 1 拍
收工条件：   if (fin_dly == 13'd64) ...                    // 要连续 65 拍才成立
```

- 看门狗到点那一拍条件成立，`fin_dly` 加 1（0→1）；下一拍 `ld_wdog` 已经变成
  `0x7FFFFF1`，条件不成立，`fin_dly` **就停在 1**——收工条件永远凑不满 64。
- `ld_wdog` 是 28 位且**不饱和**，`2^28 / 37.5MHz = 7.16s` 后回绕到 0。
- 回绕那拍 `ld_wdog == 0` 成立 → **`prog` 被清零**。

于是每次加载卡住时看到的就是：

| 时间 | 数码管 | 说明 |
|---|---|---|
| 0 → 2.77s | `00→99` | 99 个 tick × 27.96ms |
| 2.77s → 7.16s | `99` 不动 | 看门狗回绕前的空转 |
| 7.16s | `00` | 回绕 → 进度清零重走 |
| 14.3s / 21.5s / 28.6s | `00` | 再来一遍 |

**4 × 7.16s = 28.6s ≈ 用户说的"接近 30 秒"；每次切图看到 3~4 次 `0→99`
就是 4 次回绕。** 而 `load_cnt` 只在"进入 LD_LOAD"时 +1，所以始终是 1 —— 这个
数字正好把"反复加载"排除了。

## 2. 修复：计时只做一件事

```verilog
// 唯一计时源：从"开始换图"那一拍起，饱和，绝不回绕
wire ld_start = (ld_st == LD_SHOW) && (nav_step || (dbg_scale != scale_d));
wire ld_run   = (ld_st != LD_SHOW) && (ld_st != LD_WAIT);
wire ld_tmo   = (sw_tmr >= 28'd127_500_000);       // 3.4s，电平
always @(posedge clk_pix ...)
    if (!rst_n)        sw_tmr <= 0;
    else if (ld_start) sw_tmr <= 0;                 // 只有这里清零
    else if (ld_run && sw_tmr != 28'hFFFFFFF) sw_tmr <= sw_tmr + 1;
```

- 进度：`prog_tick = sw_tmr[19] & ~wd19_d`，清零条件只剩 `ld_start`。
  **加载过程中任何情况都不会清零**，`0→99` 永远只走一次。
- 超时：`ld_tmo` 是**电平**，一旦到点就一直保持到下一次切图，
  `fin_dly` 必定能数到 64，硬超时 100% 生效（旧版是"看运气"）。

## 3. 顺手补掉的挂死点（reader / sd_read）

| 位置 | 问题 | 现在 |
|---|---|---|
| `sd_bmp_reader.S_TBL` | 等文件表没有退路 | 2.6ms 超时 → err |
| `sd_bmp_reader.S_F0` | 发 FAT 扇区请求**没等 `!rd_busy`**，1 拍脉冲被仲裁器吞掉 → `S_F1` 死等 | 先等 `!rd_busy` 再发 |
| `sd_bmp_reader.S_F1` | 等 busy 没有超时 | 2.6ms 超时 → 重发（4 次）→ err |
| `sd_bmp_reader.S_F2` | 收 FAT 字节半截断流就永远不走 | 2.6ms 超时 → err |
| `sd_bmp_reader.S_GAP` | 等写 FIFO 消化没有超时 | 2.6ms 超时 → err |
| `sd_read` 状态 `4'd1` | 等 R1 响应没有超时，`rd_busy` 永不落 → 整条总线死锁 | 2.6ms 超时 → 放开总线 |
| `sd_read` 收数超时 | 只清 `rd_data_flag`，`rx_flag/rx_bit_cnt/rx_data_cnt` 带着残值进下一次 | 新增 `rx_abort` 彻底清 |

## 4. 自愈：超时/读失败后重来一次

`LD_LOAD` 里新增分支：**读失败或 3.4s 超时 → 打一拍 `reinit_pulse` →
`sd_reinit`（复位 sd_ctrl_top / sd_arb / fat_mnt / fat_scan）→ 回 `LD_WAIT`
重新挂载扫描 → 再读这张图**。每次切图只重试一次（`ld_retry`），
第二次还失败才按老路收工（保留旧图 / 首张继续等）。

这样"卡一次就再也起不来"变成"最坏 3.4s 后自己复位重来"。

## 5. 数码管新格式（诊断口径）

```
加载次数 | 丢字 | 图片数 | {ld_st, sd_ready} | 切图次数 | 上次切图耗时
```

- 加载中：最左两位是进度 `00~99`。
- 静止时：`1 0 4 9 1 3`
  - `1` 本次切图进了 1 次 `LD_LOAD`（2 = 自愈重试过一次）
  - `0` 读通路丢字
  - `4` 扫到 4 张图
  - `9` = `{ld_st=SHOW, sd_ready=1}`
  - `1` 上电以来切了 1 次图（**一次按键必须只 +1**）
  - `3` 上次切图总耗时 = 3 × 0.447s ≈ 1.34s（`4`≈1.8s，`F`≥6.7s）
- 挂载/扫描错仍占用中间位：`.. F <scan_err> ..` / `.. E <mnt_err> ..`

原来的"挂载状态/扫描状态"两位被"切图次数/耗时"替换（挂载/扫描已长期稳定为 0/8）。

## 8. 追加：`204911` —— 我加的 S_GAP 超时把正常加载打死了

上板复测：按一次「下一张」图不换，数码管稳定后 `2 0 4 9 1 1`。

按新口径解码：

| 位 | 值 | 含义 |
|---|---|---|
| 1 | `2` | 本次切图进了 **2 次** `LD_LOAD` → 第一次失败后自愈重试过 |
| 2 | `0` | （当时是丢字位）0 |
| 3 | `4` | 4 张图 |
| 4 | `9` | `ld_st=SHOW`、卡就绪 |
| 5 | `1` | 只切了 1 次图 → 按键只触发一次 |
| 6 | `1` | 整次切图只用了 0.45~0.9s |

`dur=1` 直接排除了 3.4s 硬超时 → 两次加载都是**秒级以内就报错退出**。
唯一可疑的是这次新加的 `S_GAP` 写 FIFO 超时（2.6ms）：

```verilog
end else if (fu_s2 >= 9'd64) begin     // 等写 FIFO 消化
    wto <= wto + 1;                     // ← 我加的 2.6ms 超时
    if (wto == 16'hFFFF) err <= 1;      // 正常等待跨帧就被判死
```

帧缓存的写 FIFO **只在每帧帧首 16 行（`WR_LINES=16`）的窗口里排空**，
所以"FIFO 满、等消隐期"是完全正常的等待，一次就可能跨一整帧（33ms）。
2.6ms 超时 → 每个扇区第一次进 S_GAP 就判失败 → 图片再也不换。

### 修复

1. **撤掉 S_GAP 的写 FIFO 超时**（恢复原状），真的卡死交给顶层 `ld_tmo(3.4s)` 兜底。
2. **其余所有新超时统一放宽到 21ms**（`wto`/`to_cnt` 加宽到 20 位，比较 `20'h7FFFF`）：
   正常等待都在 1ms 内，21ms 只可能是真异常，避免再误杀。
3. **自愈重试的时序补丁**：`reinit_pulse` 之后 `sd_ready`/`scan_done` 要 2~3 拍才落下，
   原来 `LD_WAIT` 会立刻放行、拿着"还没挂载"的 `fat_lba/data_lba` 去读图。
   现在 `LD_WAIT` 先等 28ms 静默期（`wait_hold`），再等 `sd_ready` 重新起来。
4. **数码管第 2 位改成"出错状态快照"**（`err_st`，原来显示读通路丢字，长期恒 0）：
   出错那一拍 reader 停在哪个状态就记下来 —— `1=TBL 2=CMD 3=WT 4=RCV 5=GAP 6=F0 7=F1 8=F2`，
   `0` = 本次加载没出错。下次再出问题，这一位直接指出卡在哪一步。

## 9. 真正的慢：帧缓存写窗口只有"帧首 16 行"

`204911` 的第二个信息是 `dur` 只有 1（<0.9s）——但**之前正常时一次切图要
7~30s**。这中间差的不是 SD 速度，是帧缓存的写入节流：

```verilog
// frame_buffer.v
localparam WR_END = WR_LINES;                       // 16
wire wr_window = load_mode | (y < WR_END12);         // y = 当前帧行号
assign wf_rd = wr_win_m & ~wf_empty & ~a_vld & ~wfly;  // FIFO 只在窗口内排空
```

- 写 FIFO（256 深）**只在每帧帧首 16 行（750 行里的 2.1%）排空**；
- 读图时源一直往 FIFO 灌（4KB 簇 ≈ 1365 像素），FIFO 到 64 就把 reader
  挡在 `S_GAP`，只能等下一帧消隐期 —— **一张图要等上千帧**；
- 这才是"一次切图几十秒 / 进度条反复"的物理根源（`load_mode` 只在首张为 1，
  之后恒 0，所以后续每张图都被节流）。

### 修法：按需开窗（不动显示侧）

```verilog
assign fb_load_mode = load_mode | ((ld_st == LD_LOAD) && (fb_wf_used >= 9'd64));
```

- FIFO 没堵（`fu<64`）：窗口维持 16 行，**显示侧读通路完全不变**；
- FIFO 一堵（`fu>=64`，正好是 reader 要停下的时刻）：立刻把整帧写窗口打开，
  几个微秒就排空，reader 立刻继续；
- 写入突发仍然被 `rq==63` 节流到 1/64 的 SDRAM 带宽，不会抢显示侧的读。

效果：读图从"每帧只能进 ~256 像素"变成"按 SD 实际速率进"，
一张 960×540 的理论时间回到 1.3s 量级。

## 10. P&R：加逻辑后单点 pib 冲突 → 砍寄存器恢复"默认脚本能布通"

上板时的 `204911` 版本是**用改过的 phy_1 脚本**布出来的（CongestionHigh 变体）。
但 TD GUI 一保存工程就会把 `prj/**/phy_1/yuanshen_hdmi.tcl` 重置成默认模板
（实测 mtime 回到 16:52，参数全丢），于是用户再点布局布线就撞回单点冲突：

```
PHY-8023 ERROR: Location: (x29y14_local6), nets: rst_n_dup_226 u_core/u_spec/mux39_syn_261
RUN-8102 ERROR: Incremental route failed.
```

和 P19 的教训一样：**多出来的寄存器把布局推到临界**。这次新增约 77 个寄存器
（`sw_tmr` 28 + `wait_hold` 20 + `wto/to_cnt` 各 +4 + `err_st/st_d/sw_cnt/dur_q/...`）。

砍法（功能不变，只压位宽）：

| 信号 | 改前 | 改后 | 影响 |
|---|---|---|---|
| `wait_hold` | 20 位（28ms） | 8 位（6.8us） | 只为跳过 `sd_ready/scan_done` 的 2~3 拍滞后，6.8us 足够 |
| `wto`（reader） | 20 位（21ms） | 17 位（5.2ms） | 正常等待都 <1ms，5.2ms 仍很宽松 |
| `to_cnt`（sd_read） | 20 位（21ms） | 17 位（5.2ms） | 同上（512 字节正常 164us） |

结果：**默认脚本（无任何 set_param）直接布通**，不再依赖 GUI 会丢的参数。

| 项目 | 结果 |
|---|---|
| route | 0 违例（无 PHY-8023） |
| clk_pix 同域 | **+3.575ns / 0 违例** |
| clk_sd 同域 | **+7.551ns / 0 违例** |
| 码流 | `yuanshen_hdmi.bit` 631958 B（23:05） |
| 仿真 | `run_fat` PASS（230912 字节 0 错） |

## 11. 1.3s 达成，但切屏花屏 —— `wr_win_m` 不能中途打开

上板：`104913` —— **1.34s 切完、只读 1 次、无错**，速度目标达成；
但切屏过程中画面花屏。

原因在第 9 节那个"按需开窗"：`wr_win_m` 在读侧不是"暂停"，而是**整段复位**：

```verilog
afifo #(.DW(32), .AW(11)) u_rfifo (
    .aclr (wr_win_m | pix_rst),      // ← 窗口一来，读 FIFO 直接被清空
    ...
always @(posedge clk_mem ...) begin
    if (wr_win_m) begin              // ← 行游标也归零
        rcol <= 0; rrow <= 0; rout <= 0;
```

也就是说 `wr_win_m` 只能出现在**帧首 16 行**（读预灌之前）。中屏把它拉高，
读 FIFO 被清、行游标归零 → 画面撕裂/花屏。所以第 9 节的写法是错的，已撤销。

### 正确改法：只放开"写侧出队"，不动帧首窗口

`wr_win_m` 原本把两件事绑在一起：① 读侧复位；② 写 FIFO 出队 + 写突发。
①必须留在帧首，②可以放开：

```verilog
// 原来：assign wf_rd = wr_win_m & ~wf_empty & ~a_vld & ~wfly;
assign wf_rd = ~wf_empty & ~a_vld & ~wfly;                 // 任意时刻出队
// 写突发启动条件里也去掉 wr_win_m（其余不变）
end else if (bfull && app_init_done && ~app_ref_vld && ~app_busy &&
             (rq == 6'd63) && ~rburst) begin
```

为什么安全：
- 写突发本来就被 `wq` 限速成 **每 64 拍最多 4 字**（≈7.8M 字/s），
  而读图时源只有约 0.15M 字/s → 不会和读抢带宽；
- 读侧只占约 9% 的 SDRAM 带宽，1024 字读 FIFO（≈73us 余量）足够吸收
  一次写突发带来的几十拍延迟；
- 读侧的复位/预灌逻辑一行没动，帧首窗口照旧。

效果：读图不再被"每帧 256 像素"节流（→1.3s），显示侧读通路完全不受影响。
